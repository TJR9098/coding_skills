# 论文方法与落地差异

来源：[Rethinking Verification in Agent Harnesses, arXiv:2610.34577v1](https://arxiv.org/abs/2610.34577v1)，重点为第 3 节、第 5.4 节及附录 E.4–E.5。以下区分论文设计与本 skill 的工程选择。

## 采用的机制

- **独立上下文**：论文的 critic 在新上下文审查当前产物。本 skill 的主要场景是新对话，用户自行在同一项目中启动；不因调用 skill 自动创建或联系其他对话。
- **任务与改动优先**：默认从任务要求和 diff 建立检查，按需要读取其他源码。论文中完整轨迹的收益依任务而变，不能把“上下文越少越好”或“完整轨迹一定更好”作为通则。
- **执行与反例**：critic 能在 live sandbox 中运行检查，反馈遗漏的要求、反例及观察结果。主 Agent 根据具体反馈修复。
- **职责分离**：reviewer 检查并报告，主 Agent 修改。它降低审查者边查边改导致待审对象变化的风险，但不代表 reviewer 的运行命令天然没有副作用。

## 本 skill 主动做出的调整

- 论文实验采用 Qwen3.7-Plus 作为 critic；本 skill 不固定模型，也不暗示另开对话意味着模型权重不同或判断完全独立。
- 论文 critic prompt 强调逐条运行验证。本 skill 同时接受明确静态证据，避免为了证明显然的控制流错误而付出不必要的运行成本。
- 对不明确需求或缺失环境，本 skill 报告待确认事项或验证缺口，不把“未能证明满足”自动当成“已证明代码错误”。
- 使用标准 Code Review findings，按触发条件、影响、证据和最小修复方向交接；不强制采用论文的 `done`/`feedback`/`checklist` JSON。
- 用户要求复核时检查修复及相关回归；论文标准单轮 L3 在反馈后接受下一次交付，并未再次 review。复核是工程扩展。
- 默认单 reviewer、单轮，不把论文 scaling 实验转成必选的多 Agent 或多轮循环。

## 解读边界

- 论文 L2 中的固定拒绝完成消息不一定由真实失败触发。其结果不能推导为应取消测试驱动的完成门控。
- 宽度实验中的多个 critic 在同一 sandbox 中顺序执行，彼此不接收对方评估；有任何异议就汇总反馈，一轮修复后不再审查。不要把它描述为已验证的并行加速或多数投票。
- 论文报告的是任务子集上的平均效果及特定模型价格下的成本，不能保证本项目使用本 skill 的增益。
- 该方法是执行验证和经验性审查，不构成形式化正确性证明。目标是形成有助于修复的可信反馈，而非增加检查次数或评论数量。
