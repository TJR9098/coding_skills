# 行为评估

## 本地确定性检查

在 skill 根目录运行：

```text
python -B -m unittest discover -s tests -v
```

测试只使用临时 Git 仓库。覆盖工作区/staged/refs 范围、源文件不被修改、P/H 差异、反方向不误报、M 通过旧测试后被新测试杀死、杀死 M 但未捕获 H、筛选不通过的 M 不进入比较、未杀死 M 时仍检查 H、仅 H 的 hypothesis 测试、flaky 重跑、日志规则线索、依赖目录复制/链接与清单变更提示、`{repository}` 占位符与 NODE_PATH 只读引用（装有 Node 时运行）、能力探测不运行项目代码、超时/启动错误、证据不可覆写、Git/Python 环境归因和符号链接边界。状态验证覆盖过期证据、已关闭结论跨快照保留、作者反馈规则、证据路径与复现实验交叉校验、未确认候选和复审上限、复核结论半并入时不可交付、复核 verdict 与 review_mode 一致、复核原文路径和 `related` 引用。

这些测试验证执行与状态语义，不证明模型能可靠发现真实缺陷。

## 独立使用评估

对 skill 的实质修改，选择一个专家已确认的缺陷 PR 和一个正常/预期变化 PR。向独立 reviewer 提供 skill、原始任务、P/H 和必要环境，不泄漏缺陷位置或后续修复。分别检查：

1. 能否从需求和真实路径发现缺陷；是否把预期变化误报。
2. 动态路线是否实际执行了 P/H、已有测试和 M，而非口头声称验证。
3. 无测试运行能力时是否如实降级；工具错误是否被当作 bug。
4. 是否保持待审源码、索引和已有测试；生成物是否在隔离目录。
5. 修复后是否复测并结束；已驳回问题是否无故重开。

评估 Codex 与 Claude Code 时区分两个层次：通用流程/脚本可用，以及原生 skill 发现/调用已在对应宿主验证。不能把安装了 CLI 或文档格式符合标准当作完整兼容性测试。

宿主真实调用若因认证或运行环境受阻，记录具体限制，保留可用的手动路径调用说明。不要为了测试修改用户全局 Agent 配置或绕过权限。

持续评估记录真实缺陷召回、误报/有害修改、审查轮数、人工确认时间和运行成本。历史事故回放不得向待评估 Agent 提供后续答案；每次模型/提示词变化保留同一输入比较。

## 回归评估集与取舍规则

做法参照 Claude Code 团队用事故做评估集：

1. **评估集**：已确认缺陷的 PR（历史回滚、事故，或 ReviewBench、CRBugBench 中有专家标注的样本），每例由熟悉代码的人确认缺陷位置；另取一组已知干净的 PR。每遇到 skill 漏报的真实缺陷就加一例。
2. **消融**：同一输入分别以 `quick`、`standard`（静态 + hypothesis）、`standard + dodgy-diff`、`deep` 运行。每组至少记录：命中的真实缺陷数、干净 PR 上会导致有害修改的 finding 数、平均复审轮数、模型 token 与命令耗时。
3. **取舍**：对 skill 的提示、策略、脚本或模型的任何修改，都在全集上重新评分。召回优先，减少轮数其次；召回不升且干净 PR 误报不降的修改不保留。某个动态策略在消融中不带来额外召回时，从默认档位移除，而不是默认继续执行。
4. **交付**：有时限的评测分别统计发现的候选数、发出复核数、复核返回数、确认数、成功导出数和超时数，不只看最终 precision。超时的例子保留在分母中，不补写其记录。
5. **噪声**：真实使用中按 `author_response` 统计 `fixed`、`wrong`、`intended`、`not_worth_it` 的比例；`wrong` 与 `not_worth_it` 上升说明需要收紧上报门槛，同一类问题反复出现时检查 `source_fix_suggestions` 是否已落地。

裁判模型只能辅助匹配 finding 与标注缺陷；结论需抽样人工复核，不能把输出数量当作命中数。

历次验收结果记录在 skill 根目录的 `CHANGELOG.md`，不放在本文件。
