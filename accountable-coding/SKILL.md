# Accountable Coding

用户最终要为交付的代码负责：出了问题，要能解释、能担保的人是用户，不是 agent。
agent 的输出通常写得规整、测试也是绿的，正因为看起来已经完成，用户很容易跳过检查，慢慢变成"签字但说不清为什么"。

这个 skill 的目的是让用户的判断落在两端：
- **动手前**：把意图说清楚，并且约定好怎样才算对；
- **结束时**：拿到真实证据，看到 agent 替他做了哪些决定。

中间的执行由 agent 完成，但要用程序验证，而不是靠自我感觉。

多问几个问题、多列几行清单都有成本，所以先按风险分级，只在值得的地方投入。

---

## 0. 判定风险等级

| 等级 | 判定标准 | 流程 |
|---|---|---|
| 低 | 不改变程序行为的改动（typo、注释、格式化、只在局部作用域内的重命名），或一次性脚本、探索性代码 | 不提问（除非有歧义）；跑已有检查；回复末尾用 1–2 行说明假设和未验证项 |
| 高 | 涉及事务边界、并发、权限/认证/安全、数据迁移或删除、性能关键路径；或**修改已有的**公共接口（API、schema、配置格式、对外函数签名） | 完整流程，并叠加异构检查（见 2.5） |
| 中 | 其余情况，包括**新增**函数、接口或配置项 | 完整流程 |

**"已有"和"新增"为什么要分开？**
- 修改已有接口或格式，会影响已经依赖它的调用方和线上配置，出错的影响面不可控。
- 新增的东西还没有使用者，出错的影响面有限，按中风险处理即可。
- 但新增内容一旦定义了格式（例如新的配置写法），格式规则要在 brief 里问清楚，因为上线后再改就变成了"修改已有格式"。

**边界示例**：
- 局部变量改名、修注释拼写 → **低**：行为不变，跑已有测试即可。
- 把配置值、默认值、常量、阈值或判断条件改掉，哪怕只改一行（如超时 30→60） → **中**：行为变了。先搜索所有使用点，再跑已有测试，并在回复里写明连带影响。
- 新增 `parse_duration` 供配置使用 → **中**：新增函数，但它定义了新的配置写法，格式规则要先问清。
- 修改已导出函数的返回值类型、抛出的异常类型或参数含义 → **高**：属于修改已有公共接口。
- 复核另一个 agent 对转账并发问题的修复 → **高**：同时涉及并发和资金。

**判不准时按高一级处理。** 把低风险当成中风险，代价是多问一两句；反过来，代价是带着未验证的假设上线。

**执行中发现实际风险更高时，立即升级并告诉用户。** 例如原以为只是重命名，结果名字是对外导出的；或者修一个 bug 时发现它在事务里。

## 1. 动手前：建立 brief

### 1.1 先推断，再追问

1. **推断**。从用户请求、对话历史和代码库里，推断出下面四项：
   - **目标**：要解决什么问题，给谁用；
   - **不做什么**：明确的范围边界；
   - **完成的定义**：交付物是什么，到什么程度算完；
   - **验证通过的标准**：具体到可执行的检查。例如"`pytest tests/test_parse.py` 全部通过，且新增用例覆盖 A、B、C"，或"P99 延迟从 X 降到 Y 以下"。

2. **只追问缺失或有歧义的部分**。用户已经说清楚的不要再问。
   - 问题一次问完，不要一轮挤一个。
   - 尽量给出你的推测或几个选项让用户选，这样用户回答起来成本更低。
   - 常见的歧义点：
     - 输入的范围和边界；
     - 非法输入怎么处理（抛异常、返回空值还是记录日志）；
     - 兼容性要求；
     - 性能目标；
     - 新行为与现有行为冲突时以谁为准。

3. **复述 brief，等用户确认后再动手。**

"验证通过"必须是能跑出结果的检查，不能是"看起来能用"。原因是：等做完再定义标准，人和 agent 都会不自觉地把手头的结果合理化成"达标"。

### 1.2 brief 模板

```
**Brief**（风险：中）
- 目标：…
- 不做：…
- 完成的定义：…
- 验证通过 = …（具体命令 / 用例 / 指标）
- 我的初步判断：问题可能在… / 打算这样做…（这是假设，欢迎推翻）
- 需要你确认：1. … 2. …
```

"初步判断"这一行的作用，是让用户在你投入大量工作之前就有机会纠正方向。用户一旦先看到一份完整、流畅的方案，就很难再想到别的可能。

**需要新写测试时（见 2.2），把测试场景表和 brief 放在同一条消息里发出。**
- 场景按你在"需要你确认"里给出的推测来写。
- 这样用户一次就能确认需求和"什么算对"，少一轮来回。
- 用户改了某个推测，你再相应调整场景即可。

### 1.3 用户说"别问，直接做"或无人值守时

- 采用最合理的理解开工，在回复开头用一两句话写明你采用了哪种理解。
- 所有推断出来的需求，都在最终清单的"假设"里标为**未验证**。
- 不可逆的操作仍然要停下来问。例如：删除数据、迁移生产库、force push、对外发布、改动共享环境。

### 1.4 低风险任务

- 跳过 brief，除非请求本身有歧义。

## 2. 执行中：用程序验证

### 2.1 先找现成的验证手段

1. **找**。动手改代码前，先查看项目已有的验证手段：
   - 测试目录；
   - CI 配置；
   - Makefile、`package.json` 等文件里的脚本；
   - lint 和类型检查配置；
   - 已有的 benchmark。
2. **先跑一次基线**，记下改动前的状态：哪些用例已经失败、指标是多少。
   - 不知道基线，就分不清失败是旧的还是你引入的。
   - 性能优化类任务没有基线，就无从比较。

### 2.2 没有现成测试时：拟场景 → 确认 → 先测试后实现

**第一步：从需求出发拟测试场景，并标注每条对应哪项需求。**

```
| # | 场景 | 输入 | 期望结果 | 对应需求 |
|---|---|---|---|---|
| 1 | 正常路径 | … | … | 需求 1 |
| 2 | 边界 | … | … | 需求 1 |
| 3 | 非法输入 | … | … | 需求 2 |
```

- 覆盖三类：正常路径、边界、非法或异常输入。
- 重构和优化类任务，以旧实现的输出为参照做差分测试：行为应当完全一致，除非 brief 里写明了允许的差异。

**第二步：把场景清单发给用户确认。** 测试场景定义了"什么是对的"，这件事应当由用户拍板。通常和 brief 放在同一条消息里发出（见 1.2）。

**第三步：用户确认后，按以下顺序执行。**

1. 先写测试。
2. 如果被测的函数或类还不存在，先放一个只抛 `NotImplementedError`（或所用语言的等价写法）的桩。
   - 不放桩时，测试会以导入错误或编译错误整体失败，看不出每条用例是否写对了。
   - 放了桩，测试能被正常收集，每条用例都会因为功能缺失而单独失败。
3. 运行测试，确认它**失败**，并且每条用例的失败原因都是功能缺失（例如全部是 `NotImplementedError`），而不是测试本身写错。
4. 再写实现，替换掉桩。
5. 运行测试，确认通过。

**为什么要先见红？**
- 实现和测试如果出自同一套思路，就会共享同一个错误假设，然后一起变绿。
- 测试来自需求、写在实现之前、先失败过一次，才能说明它真的能抓住问题。

**不要为了让测试通过去改测试的期望值。**
- 如果你认为某条期望本身错了，停下来，说明理由，请用户决定。
- 期望值代表需求。悄悄改掉它，等于替用户改了需求。

### 2.3 无法运行时

聊天环境里没有执行条件、缺依赖、需要特定硬件或外部服务时，按以下方式处理：

- **能跑的部分照样跑**：在沙箱里跑纯逻辑部分，或者写一个最小复现脚本。
- **跑不了的部分**：
  - 给出用户可以直接执行的验证命令和预期输出；
  - 在最终清单的"未验证与风险"里列出来。
- **不要写"已验证"**。没运行过的检查只能算计划，不能算证据。

### 2.4 证据 → 决策 → 理解

以下四种情况都走这三步：
- 执行中测试失败或报错；
- 修复用户报告的 bug；
- 处理 code review 意见，包括其他 agent 的 CR 和它已经做出的修复；
- 你自己发现的问题。

**第一步：证据。先复现，再修。**
- 记录复现步骤、期望与实际的差异、关键日志或堆栈、失败的用例。
- CR 意见也要先验证它是否成立。CR 可能看错，也可能把问题的严重程度判断错。
  - 能写出失败用例就写；
  - 写不出来，就说明为什么认为它成立，或不成立。

**第二步：决策。**
- 选定的修法和理由；
- 考虑过但放弃的备选，以及放弃的原因；
- 影响范围：会不会改变别处的行为。

**第三步：理解。把根因讲到用户能复述的程度。** 需要回答三个问题：
- 问题为什么会发生；
- 这个修法为什么能解决它；
- 之前的测试为什么没抓住它。

最后加一个回归测试，同样要先红后绿：它必须在修复前的代码上失败。在修复前能通过的回归测试，说明它根本没有测到这个问题。

**依赖时序的问题要特别处理。** 竞态、超时、乱序到达这类问题，常规运行中可能跑几百次都不触发。
- 复现不了时，不要直接得出"问题不存在"或"已经修好"的结论。
- 可以用插桩扩大时间窗口，例如在读和写之间主动让出调度、注入延迟、用屏障（barrier）让线程同时开始。
- 在证据里注明用了插桩，以及不插桩时的结果。
- 回归测试也可以带上插桩，前提是只放在测试代码里，不进入生产代码。

**复核其他 agent 已经做出的修复时，同样走完这三步。**
- 不要因为"已经修好了"就跳过复现。
- 已有的修复也可能引入新问题，例如锁顺序不一致导致死锁、异常类型变了、边界行为被翻转。

记录格式：

```
**问题**：…
- 证据：复现方式 / 期望 vs 实际 / 关键输出
- 决策：修法 + 理由；放弃的备选：…（原因）
- 理解：根因…；这个修法有效是因为…；原测试漏掉它是因为…
- 回归测试：`test_xxx`（修复前失败，修复后通过）
```

### 2.5 高风险改动：叠加异构检查

**为什么需要异构检查？**
- 你写的测试和你写的实现，可能有同样的盲点。
- 用同一个模型在新上下文里自审，能去掉会话里积累的偏差，但去不掉模型本身的系统性盲点。

**因此，高风险改动至少叠加一种不依赖你自己判断的检查。** 按适用性选择：

- 静态分析、类型检查、linter；
- 运行时检测工具：race detector、ThreadSanitizer、AddressSanitizer 等；
- 属性测试、模糊测试：针对你没想到的输入；
- 差分测试：与旧版本或参考实现对比输出；
- 在真实环境或集成环境中运行；
- 并发问题：用多线程或多进程的压力测试复现，并检查死锁（例如两个方向同时操作）；
- 新上下文的子 agent 审查（如果环境支持）。它可以作为补充，但不能作为唯一的异构检查。

在最终回复里写明：用了哪些检查，各自覆盖什么，还剩什么没覆盖。

## 3. 结束前：先证据，后总结，再清单

用户读回复时最先看到的应当是事实，而不是 agent 对自己工作的叙述。总结写得再好也只是叙述，命令和输出才是证据。

**中、高风险任务的最终回复，按这个结构写**（标题用用户使用的语言）：

```
（第一行：一句话结论。例如"可以合并"、"不能按原样合并，原因是…"、"已完成，20 个用例通过"）

## 验证证据
- 执行：`实际运行的命令`
- 结果：关键输出原样摘录（通过/失败数、指标数值、关键日志行）
- 这些检查证明了：…
- 这些检查没有证明：…

## 问题与修正（仅在修过问题时出现）
- 问题 1：证据 / 决策 / 理解，按 2.4 的格式，压缩到 5 行左右

## 改动摘要
2–5 行，说明改了什么。

## 关键决策
1. 决策内容 — 理由；放弃的备选：X（原因）

## 假设
- 假设内容 — 已验证（怎么验证的）/ 未验证（建议怎么验证）

## 范围外
- 判断为范围外、因此没做的事 — 原因

## 未验证与风险
- 没有验证的地方 — 可能出错的具体场景
```

### 3.1 写清单的要点

- **证据只来自本次会话里真实运行的输出。** 不要凭记忆或预测填写。没跑就写"未运行"及原因。
- **"没有证明什么"必须写。** 绿灯只代表那几条检查通过了。例如测试覆盖了单线程，就要写明没覆盖并发。
- **"关键决策"指你替用户做的选择。** 常见的有：
  - 默认值；
  - 错误处理方式；
  - 需求冲突时的取舍；
  - 数据结构或算法的选择；
  - 接口的形状；
  - 引入的依赖；
  - 比原需求做多或做少了。
  
  中、高风险任务如果这一节是空的，通常说明你没有意识到自己做了决定，应该回头检查一遍。
- **每条都要具体到用户能据此行动。** 例如：
  - 写"未测试 Windows 路径分隔符"，不要写"可能存在未知问题"；
  - 写"假设时间戳均为 UTC，未验证；可在 X 处加断言确认"，不要写"假设输入合法"。
- **某一节确实没有内容时写"无"**，不要为了凑数而编造。

### 3.2 控制篇幅

回复越长，用户越容易只读开头就签字，清单也就失去了作用。所以要短到用户愿意读完，同时不丢掉会改变判断的信息。

- **证据只摘关键行。**
  - 每条命令只摘通过/失败数、关键指标和 1–2 行关键日志，不贴整段输出。
  - 几个结果相近的检查合并成一张表。
- **每节最多 5 条，按影响从大到小排序。**
  - 超出的部分不要删掉不提，在末尾注明"另有 N 条较次要的，需要时可展开"。
  - 排序时，会让用户改变"能否合并 / 能否上线"判断的条目放在最前面。
- **每条写一到两行。** 理由只写关键的一句，不展开推理过程。
- **压缩的是每节的内容，不是小节本身。**
  - 关键决策、假设、范围外、未验证与风险这四个标题都要保留，没有内容就写"无"。
  - 用户靠这几个固定位置，快速找到需要自己判断的地方。
  - 不要把它们并进"问题与修正"，也不要换成别的标题。
- **同一件事只说一次。**
  - 已经在"问题与修正"里讲过的决策，在"关键决策"里只写"见问题 1"。
  - 已经写在"未验证与风险"里的内容，不要在"假设"里再展开。
- **整体篇幅参考**（不含代码块）：
  - 中风险：约 30 行；
  - 高风险：约 50 行。
  
  超出时，先删重复内容，再合并同类条目。

### 3.3 低风险任务的收尾

用 1–2 行收尾即可：

```
验证：`ruff check report.py && pytest -q` 通过（12 passed）。
假设：`tmp_lst` 只在函数内部使用，已用 grep 确认；未验证：无。
```

## 常见失误

- 把"测试通过"当成"需求满足"，没有说明测试覆盖了什么、漏了什么。
- 为了让测试变绿，修改测试的期望值，或者跳过、删除失败的用例。
- 没运行过的检查写成"已验证"，或者把预期的输出当成实际输出。
- 用户没说过的需求，被你当成既定事实写进实现，却没在"假设"里标出来。
- 复核别人的修复时，只读了 diff，没有复现原问题，也没检查修复的副作用。
- 先写一大段总结，把证据埋在后面，或者完全不给证据。
